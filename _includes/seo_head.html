{%- comment -%} On-page head metadata for every page (2026-09-27, on-page SEO pass). WHY THIS FILE EXISTS INSTEAD OF `{% seo %}` (jekyll-seo-tag 2.9): jekyll-seo-tag was emitting, on all 311 pages: * TWO tags - one hand-rolled in `_layouts/default.html` from `page.excerpt` (which fires FIRST and therefore wins in every consumer that takes the first match, and which collapses to one identical site-wide sentence on the 233 pages that have no excerpt), and a second from the plugin. jekyll-seo-tag 2.9 has no `description=false` switch - only `title=false` and `canonical=false` - so the duplicate could not be suppressed from the outside, only worked around by not calling the tag at all. * a `BlogPosting` JSON-LD node on 302 pages, including 68 video records, 68 transcripts and 20 academic papers, and no `author` on any of them. The plugin cannot know about this site's four custom collections, and it has no way to be told. * `og:title` = `page.title`, so the homepage announced itself as "Home", and no `og:image` anywhere on the site, so `twitter:card` was pinned to the small `summary` card on all 311 pages. * a `description` truncated to a WORD count, not a character count, which is how descriptions reached 671 characters. The plugin stays enabled in `_config.yml` (that file is not this pass's to edit, and leaving it is harmless); it is simply no longer called. Everything below is emitted by this archive, so every field is one this archive can account for, and nothing is emitted that the data does not contain. INPUTS `include.rendered` : the already-rendered page body, passed by `default.html` as the `content` template variable. Note the `include.` prefix: Jekyll 4.4's include tag publishes its parameters ONLY as `include.` (`context["include"] = parse_params(context)` in `lib/jekyll/tags/include.rb`), so a bare `{{ rendered }}` inside this file silently resolves to nothing. The social image is read out of the rendered body rather than out of front matter, because the images on this site live in the recovered post bodies and are not declared in any front-matter key - so the page's own social image is, by construction, the image that page actually displays. Never invented. ORDERING RULE: every branch below reads a field the page's own generator wrote. If a field is absent the corresponding tag is simply not emitted. There are no placeholder strings anywhere in this file. {%- endcomment -%} {%- comment -%} ------------------------------------------------------------------ 0. Which kind of page is this? `page.layout` is the primary discriminator, because every document in the site declares or inherits exactly one and it is what Jekyll itself used to choose the layout. The front-matter key checks come FIRST, and only for the three collections whose layout arrives through `_config.yml` defaults, so the classification does not depend on defaults being applied. The order matters in one specific place, and getting it wrong is a real bug: a catalogue entry under /articles// carries `local_post` (the path of the recovered post that holds its text) and a `slug`, while the post page itself carries `provenance` and `word_count`. An earlier version of this file tested `local_post` first and classified every catalogue entry as a full-text page, which produced the title "Full text: X" on a page that holds no text and a description with an empty capture id in it.
