A real publication date, or none. STRICTLY KIND-DRIVEN, and this is the whole point of the section. The trap: Jekyll does not leave `page.date` empty for a document whose front matter has no `date` - it substitutes `site.time`, the BUILD CLOCK. An earlier version of this file fell through to a generic `else` that read `page.date` for anything that was not a paper, a video or a transcript, and consequently published the build clock as `datePublished` and `article:published_time` on all 17 MDI pages - they are generated with `publication_date`, never `date`. It also made the build non-deterministic: two builds of an unchanged tree differed in those 17 pages, in the sitemap's <lastmod> for them, and in feed.xml. So each kind names the key its generator actually writes, and nothing else is read: paper `publication_date` - shape-checked exactly as _layouts/paper.html prints it (year-only and year-month are NOT pushed through the date filter) post `date` - a Jekyll post always has an authored date work `date` - build_articles writes it from the data row notice `date` - build_notice_pages writes it mdi_text none - build_mdi_pages writes `publication_date` in a HUMAN-READABLE shape ("February 7, 2016"), not ISO, and no `date` at all. Feeding that to the `date` filter is the exact hazard _layouts/paper.html documents, and the build clock is far worse than no date, so the field is omitted. video, transcript, home, index, 404 none - the archive records no upload date and no capture date for a recording, and a site page has no publication date. And a structural backstop that cannot be forgotten: if a date value ever arrives that is not midnight in the site timezone, it is a build clock, and it is dropped.
